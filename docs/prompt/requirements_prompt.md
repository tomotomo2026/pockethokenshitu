# 統合要件定義書作成プロンプト（Cursor用）

あなたはプロダクトマネージャーとシステムアーキテクトの両方の経験を持つエキスパートとして、ビジネス・プロダクト情報から詳細な要件定義書を**一気通貫で**作成してください。

## 入力情報

### ビジネスモデル・プロダクト・制約条件情報
`docs/input/` フォルダ内のファイルを参照してください。これらのファイルには、以下のような情報が含まれている可能性があります：
- ビジネスモデル（例: リーンキャンバス、解決する課題、価値提案、収益構造、コスト構造）
- 競争優位性分析（例: 7Powers）
- プロダクト情報（例: ターゲットユーザー像、ユーザー課題、市場規模、競合分析、差別化要因）
- 制約条件（例: 開発予算、期間、チームスキル、技術的制約、法的要件）

### 既存ドキュメント / 参考アウトプット
- `docs/output/requirements_specification.md`: 既存バージョンがあれば最新情報に基づいて更新する（無い場合は新規作成）
- その他、関係者から提供された資料があれば同様に参照し、使用したものは本文内や注記で出典として示す

### 出力テンプレート
`docs/template/Requirements_Specification_Template.md` を参照し、このテンプレート構造に従って出力してください。

**全ての利用可能な入力情報を総合的に判断し、テンプレート形式に沿った一貫性のある要件定義書を作成してください。**

## 実行プロセス

以下のステップを**順次実行**してください：

### ステップ1: 情報収集とギャップ確認
1. `docs/input/` 内の全ファイルと既存アウトプットを一覧化し、内容の鮮度と重複を確認する
2. 情報不足や不整合を早期に洗い出し、仮定候補とフォローアップ質問をメモする
3. 参照したファイル名・更新日時を控え、後で各セクション内に出典や仮定として明示できるようにする

### ステップ2: テンプレートへのマッピングと詳細化
1. `docs/template/Requirements_Specification_Template.md` の各セクションを確認する
2. ステップ1で整理した情報をテンプレートの対応セクションへマッピングし、矛盾が出ないよう構造化する
3. テンプレートに必要な詳細度まで情報を具体化する（ユーザーストーリー、機能詳細仕様、非機能指標など）
4. 不足情報は `(仮定)` や `(要確認)` として明示し、テンプレート内の該当箇所および「追加情報リクエスト」セクションに反映する
5. 参照・更新したファイルを各セクションの記述内または補足に明示する

### ステップ3: 検証と仕上げ
1. 本プロンプト末尾の評価基準に照らしてセルフレビューする
2. 表・数値・用語に説明が付与されているか、テンプレートの必須項目が埋まっているか確認する
3. 「追加情報リクエスト」に優先度付きの質問が揃っているか最終確認する

## 出力形式

### 詳細要件定義書（最終アウトプット）
- **ファイル名**: `docs/output/requirements_specification.md`
- **形式**: `docs/template/Requirements_Specification_Template.md` の構造に従い、収集した情報を統合して作成する
- **ポイント**: 各セクションで参照元（ファイル名や仮定）を自然な形で示し、必要に応じて本文または注記に `(仮定)` `(要確認)` を付記する

以下は詳細要件定義書の各セクションを埋める際の着眼点：

### 1. プロジェクト概要
- **プロジェクト名**: プロダクト情報から適切な名称を設定
- **背景・目的**: ビジネスモデル情報（リーンキャンバス）の「解決する課題」「目的」を記載
- **ビジョン / スコープ**: プロダクト情報と制約条件から、実現可能な範囲を明確化

### 2. ビジネス要件
- **ビジネスモデル情報**: リーンキャンバス、7Powers分析の要約
- **成果指標（KPI/KGI）**: ビジネス目標から具体的な数値目標を設定（必要に応じて仮定を明記）
- **ビジネス上の制約**: 制約条件ファイルから予算・期間・リソース・法的要件を記載

### 3. ユーザー要件
- **ユーザープロファイル / ペルソナ**: ターゲットユーザー情報から具体的なペルソナを作成
- **ユーザーストーリー**: 「〇〇として、△△がしたい。なぜなら□□だからだ。」形式で3〜5個作成
- **MVP の定義**: コア機能に絞ったMVP範囲を明確化

### 4. 機能要件
- **機能一覧 / MoSCoW 分類**: 
  - コア機能、差別化機能、付加価値機能を識別
  - Must / Should / Could / Won't で優先度を分類
  - MVP対象かどうかを明記
- **機能詳細仕様**: 
  - 主要機能（3〜5個）について以下を記載：
    - 概要
    - ユースケース
    - 前提条件（利用するSaaS等）
    - 正常系フロー
    - 例外系フロー
    - UI要件
    - 非機能面の注意点
  - API 連携や外部サービス利用がある場合は、前提条件やユースケースの補足として明記する

### 5. 非機能要件
- **パフォーマンス要件**: ターゲットユーザー規模から推定（根拠と仮定を明記）
- **セキュリティ要件**: 認証/認可、データ保護、監査ログ、コンプライアンス
- **可用性・信頼性**: 稼働率、バックアップ方針、DR対応
- **ユーザビリティ / UI・UX**: アクセシビリティ、多言語対応、操作導線
- **スケーラビリティ**: 水平/垂直スケーリング、突発的アクセス増対策

  - API 連携や外部サービス利用がある場合は、前提条件やユースケースの補足として明記する

### 6. 開発プロセス / スケジュール
- **開発モデル**: アジャイル / ウォーターフォール等
- **フェーズ分けされた開発計画**: 
  - 各フェーズの期間、主なタスク
  - フェーズ分けの根拠（MVPへの注力、リスク軽減、技術的依存関係など）
  - 開発フェーズごとの主要リスクや依存関係、運用・費用に関する懸念点は、このセクションの補足として整理する

## 不足情報への対応

入力ファイルが存在しない場合や必要な情報が不足している場合：

1. **情報の不足箇所を明確化**
   - 具体的にどの情報が不足しているかを明示
   - 情報カテゴリ（ビジネスモデル、プロダクト情報、制約条件）ごとに整理

2. **仮定を置く場合**
   - 合理的な仮定を置き、`(仮定: 〇〇)` として明記
   - 仮定が要件に与える影響を評価

3. **要確認事項**
   - 情報が完全に不足している場合は `(要確認)` と記載
   - 「追加情報リクエスト」セクションで、必要な情報と優先度（高・中・低）を明記

4. **フォローアップ質問**
   - 不明点がある場合、以下のような質問を行う：
     - 収益化のメカニズムをより具体的に説明していただけますか？
     - 想定している処理量や負荷はどの程度ですか？
     - 初期のターゲットユーザー数はどの程度を想定していますか？
     - 特に技術的なチャレンジが予想される機能はありますか？

## 評価基準

生成された要件定義書は以下の基準で評価されます：

### 1. 明確性
- 具体的で測定可能な目標が設定されているか
- 機能の範囲が明確に定義されているか
- 価値提供の方法が具体的に説明されているか

### 2. 一貫性
- ビジネスモデルとの整合性
- 競争優位性（7Powers）との整合性
- 制約条件との整合性
- 各セクション間の整合性

### 3. 実現可能性
- 技術的な実現可能性
- 予算内での実現可能性
- 期間内での実現可能性

### 4. 網羅性
- テンプレートの全セクションが埋められているか
- 必要な要素が漏れなく含まれているか
- ステークホルダーの要求が反映されているか
- リスクや制約が考慮されているか

### 5. 詳細度
- 開発チームが実装に着手できるレベルの詳細度か
- ユーザーストーリーや機能詳細仕様が具体的か
- 非機能要件が定量的に記載されているか

### 6. 仮定の妥当性
- 置かれた仮定は合理的か
- 仮定が要件に与える影響は適切に評価されているか
- 仮定が明示的に記載されているか

### 7. トレーサビリティ
- 各セクションで参照した情報源や仮定が明示されているか
- 記載内容同士で矛盾がなく、依存関係が明確か
- 追加情報リクエストが不足情報のカバレッジを示しているか

## 出力時の注意事項

- テンプレート形式に厳密に従うこと
- 専門用語（SaaS, JWT, CSRF, XSS, DR, WCAG等）を使用する場合は、簡潔な説明を併記すること
- 表形式のセクション（機能一覧、スケジュール等）は、マークダウンテーブルで見やすく整理すること
- セクションごとに具体例を含めること
- 不足情報や仮定は必ず `(仮定)` `(要確認)` として明記すること
- 最終的に、このドキュメントが開発チームの実装指針となることを意識すること

## 追加情報リクエスト

より正確な要件定義のために必要な追加情報のリストを、詳細要件定義書内の「追加情報リクエスト」セクションで以下の形式を参考に整理してください：

| 質問項目 | 不足情報の内容 | 影響範囲 | 優先度 |
| -------- | -------------- | -------- | ------ |
| 例: ターゲットユーザー数 | 初期および1年後の想定ユーザー数が不明 | 非機能要件、インフラ設計、費用見積もり | 高 |
| ... | ... | ... | ... |
